# Lightreason experiment history

**LR** names the configurations built and measured in this repository. The speedups come from running those configurations on one RTX 4090 with the original Qwen BF16 targets. Each published result names its comparison runner, prompt or suite, and output check. [Performance and chart data](performance.md) · [Coding prompts and results](coding-benchmarks.md)

## Upstream techniques and Lightreason changes

| Area | Upstream work | What Lightreason implemented and measured |
| --- | --- | --- |
| 3B target-only | Qwen, Hugging Face Transformers, PyTorch, NVIDIA CUDA Graphs and standard KV caching | Bucketed graph replay, a token-major KV layout with fused row append, combined BF16 projections, and a conservative vocabulary screen with an original-weight recheck. [Runner](../exact3b_dynamic.py) · [Output head](../exact3b_head.py) · [CUDA Graphs](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html) |
| 3B draft-assisted | Speculative decoding and AMD’s PARD2 draft checkpoint. [Speculative decoding paper](https://arxiv.org/abs/2211.17192) · [PARD2 paper](https://arxiv.org/abs/2605.08632) · [AMD checkpoint](https://huggingface.co/amd/PARD2-Qwen3-8B) · [CAST](https://arxiv.org/abs/2610.00321) |

## Qwen2.5-3B

The target fits in VRAM. We first reduced work per decoded token, then tested how many tokens could share a single target pass. The target-only reference and the preceding draft-assisted runner remained available throughout.

| Experiment | Result and decision |
| --- | --- |
| **LR · CUDA graphs + compact KV.** Replay the same decode work with shared graph pools and 128-position attention buckets. Fuse KV append and screen vocabulary rows with an upper bound. | Retained as Lightreason Exact. The six-prompt medians were 63.0 → 139.6 decode tok/s, with 30/30 exact timing pairs and 38/38 separate validation cases. Median paired warmed request latency improved 2.19×. [Target-only benchmark](benchmarks.md#target-only-studio-runner) |
| **Train and fold a PARD2 feature adapter.** Train a projector and LoRA on the auxiliary and fold the LoRA into a separate draft copy. | The 450-update pilot reached 4.04× warmed request speed and 4/6 exact capped outputs. A higher learning-rate run improved its offline training objective but reached 3.94× and 2/6 exact, so we kept the 450-update adapter. In the uncompiled 450-update quality run, GSM8K fell from 100/128 to 99/128, with two regressions and one improvement. [Development ablations](data/qwen25-3b/experiment-ablations.json) |
| **LR · Compiled PARD2 draft.** Compile the draft query and capture the original prefill work. Verify up to 15 proposed positions per branch with a 64-node tree. | The compiled-draft pilot reached 4.52× on six prompts. Adding captured prefill reached 4.76× across 30 pairs, 15/30 exact against Hugging Face. The 160-case quality run matched the prior compiled candidate on all outputs. Against Hugging Face, GSM8K held at 100/128 with one regression and one improvement. Strict diagnostic format fell from 26/32 to 25/32. [Timings, IDs, and quality](data/qwen25-3b/compiled-draft.json) |
| **Wider trees, extra draft queries and lossless GEMM staging.** Test real verifier shapes and count all work up to commitment. | A 31-depth, 128-node pilot reached 3.44×, below the 64-node compiled path. The tested CAST-style numerical branch peaked at 64 rows. It committed 5.77 IDs in 11.68 ms at 16 rows, 6.93 in 12.03 ms at 64, and 7.18 in 13.60 ms at 128. Its alternate attention variant scored 124/160 versus 126/160 and exhausted one response budget. A second draft query achieved 81% of the one-query rate. Lossless staging plus GEMM reached 23–59% of the original GEMM rate across 18 probes. We kept the existing attention, one draft query, and the original target GEMM. [Ablation data](data/qwen25-3b/experiment-ablations.json) · [Width and profiling commands](benchmarks.md#what-else-we-tested) |
| **LR · GPU tree coordination.** Move ranking, acceptance and suffix cache writes to preallocated GPU buffers. Read a small receipt each cycle. | Retained. The host tree interval fell from 0.498 to 0.132 ms. Unprofiled held-out cycle time fell from 13.927 to 13.070 ms at the same 6.339 commits per cycle. We measured 1.062× over the previous tree runner with 36/36 held-out pairs and 160/160 regression outputs matching. Hugging Face matched 12/36 held-out pairs. The verifier still used about 9.97 ms of GPU kernel time per cycle on the profiled weather prompt. [Profile and commands](benchmarks.md#gpu-coordination-experiment) |

The selected PARD2 run trained 14.81M auxiliary parameters. Four Qwen activation taps fed a learned projector. The subsequent LoRA run used rank 16, alpha 16, separate learning rates of 1e-6 for the projector and 1e-5 for LoRA, and four microbatches per update. Training used 256 target-generated continuations and 32 development records, with evaluation cases held out. The 450-update training run took 248.71 s. Only the auxiliary copy received the folded weights. [Training and ablation record](data/qwen25-3b/experiment-ablations.json)

Reproduce the 2.19× target-only request result and the new three-language benchmark with the public Qwen checkpoint. The later PARD2 runs used the published upstream draft and a separate trained adapter pinned by SHA-256. The adapter and training data are held outside the repo, so readers with the upstream downloads alone can inspect those results and rerun the target-only path. [Public 3B setup](../README.md#run-on-a-gpu-machine) · [Adapter and benchmark commands](benchmarks.md#reproduce-with-the-matching-adapter)

## Qwen3.6-35B-A3B

The text model has 64.56 GiB of BF16 weights and the RTX 4090 has 24 GiB of VRAM. This made expert reads across PCIe and from host RAM the main constraint. The first prototype established the eager reference before we changed how weights were moved.

| Experiment | Result and decision |
| --- | --- |
| **From whole-layer copies to LR Scheduled.** Move only the experts that Qwen routes to, cache them, and read router IDs together. | The early six-token experiment went from 40.04 to 4.60 s with 4/4 exact pairs. We use the later Scheduled runner as the initial long-form baseline. [Early comparison and weight audit](../edge35b/README.md#end-to-end-generation) |
| **LR · Packed Replay.** Run overflow experts on the CPU, reuse GPU execution graphs and replay recurrent mixers. | Scheduled and the first Packed runner returned the same 341-ID arithmetic answer through EOS at 7.52 and 12.85 tok/s. The replay version reached 17.18 tok/s on the 256-token weather fixture and first differed from Scheduled at token 101. Profiling showed substantial time in expert movement and host coordination. [Packed profile and ablations](../edge35b/NATIVE50.md) · [Weather outputs](../edge35b/benchmark-suite.json) |
| **Test block verification against serial replay.** Feed identical prefixes, known continuations and forced rejected suffixes. | The real DFlash v1 pilot measured 18.50 tok/s on short coding with drafting, rejected work, transfers and commit included. On logic, the four-position run first differed at token 34. A clean serial cache still produced the tie at width four, and layer-one batched QKV differed before any routing or rollback. With placement fixed, rollback matched the same-width reference block’s cache, recurrent state and convolution history. We kept the speculative runner separate from the serial exact path. [Prefix and state diagnosis](../edge35b/NATIVE50.md#token-34-and-speculation-timing) |
| **Start from stock FreeToken, then add DFlash2.** Let the target check several tokens per expert read. | Stock BF16 reached a median 31.57 tok/s over four prompts and both HTTP modes. The seven-proposal, 15 GiB cache and host-embedding configuration reached 41.51 tok/s over four early trials. A separate 8 → 16 width trial increased train-prompt transfers from 28.40 to 47.92 GB, outpacing the increase in commits. Fifteen proposals later reduced decode rates in all eight measured pairs. We retained seven proposals and eight target positions. [FreeToken and width comparisons](../edge35b/NATIVE50.md#freetoken-bf16-comparison) |
| **Reduce uncached prefill and repeat CPU reads.** Fetch selected rows in prefill. During decode, compute repeated routes together and keep the original accumulation order. | Weather first text fell from 2.38 to 1.24 s in the selected-prefill trial. The fused CPU retest gained 1.62% in median paired decode throughput with 8/8 exact pairs. The 16 GiB cache trial ran out of KV space. A 15.5 GiB trial changed all eight paired outputs and slowed the first streamed weather comparison. We kept the 15 GiB cache. [Prefill and cache trials](../edge35b/NATIVE50.md#uncached-prefill-and-cold-experts) · [CPU fusion and width tuning](../edge35b/WIDTH_AUTOTUNE.md) |
| **LR · Ada gather + DFlash2, then shared host packing.** Reconstruct original BF16 bits into GPU slots and let AVX2 read the same host format. | The first packed gather lowered payload by 8.47% but slowed weather from 38.08 to 37.06 tok/s. Native Ada unpack improved the corresponding raw control from 38.84 to 39.22 tok/s. Sharing the layout across 34 layers raised weather from 42.84 to 45.80 tok/s versus 20 layers, with 21/21 exact pairs. Two 37-layer attempts stopped during preparation after stale temperature readings, before any timed run. [Transport and layer experiments](../edge35b/EXPERT_TRANSPORT8.md) |
| **LR · Packed GPU replicas.** Keep more previously selected expert rows on the card without changing the primary planner. | An 880 MiB arena held 187 packed experts versus 146 raw. The streamed coding median rose from 50.39 to 51.08 tok/s versus fixed eight. All 20 pairs matched that control’s IDs, stop and commits. Packing the primary cache into a staged prefix doubled standalone expert layer time from about 0.18 to 0.36 ms. The direct packed kernel changed expert outputs, and the compact-tail variant changed planner capacity and output IDs. We kept the replica tier. [Replica and primary-cache trials](../edge35b/THROUGHPUT100.md) |
| **Tune DFlash2 and verifier width together.** Compare separate four-, six-, and eight-position graphs and test saved continuations as an acceptance diagnostic. | Adaptive width reached 54.23 streamed tok/s on coding, with 0/60 exact candidate comparisons across the three arms. Saved arithmetic continuations reached 67.34 tok/s on 30 matching passes before diverging. Even there, gather took 85.98 ms per pass, above the 80 ms budget for 100 tok/s at eight commits. The fixed-eight packed runner remains the exact comparison against its fixed-width control. [Joint tuning, profiles, and reproduction](../edge35b/THROUGHPUT100.md#joint-dflash2-and-verifier-tuning) |

To repeat the 35B path, run Scheduled, establish FreeToken BF16 on the same prompt IDs, then apply the patch stack and compare packed against the fixed-eight reference. Use separately captured verifier widths for development and report held-out timings with profiling off. Keep time to first text, complete request time, and startup separate. Rebuild and validate the CUDA gather and CPU worker placement on your hardware before comparing rates. [Pinned downloads and build commands](qwen35b.md) · [Hardware and agent guide](porting.md)
