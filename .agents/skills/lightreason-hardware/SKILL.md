# Lightreason hardware optimization

Read `docs/porting.md` for the backend workflow. Use `README.md` and `docs/benchmarks.md` for 3B, or `docs/qwen35b.md` for the 35B Scheduled and FreeToken runners. The comparisons and their reference outputs are described in `docs/performance.md`.

1. **Establish a device-local baseline.** Run the original Hugging Face BF16 path for 3B or the Scheduled BF16 path for 35B. Record the runtime, stock hardware settings, free VRAM and BF16 support. For 35B offload, include host RAM, link generation and width under load, and CPU affinity. The custom Ada gather targets SM 8.9. On another backend, establish the reference and test the required kernels there before claiming a port.
2. **Freeze the contract.** Preserve target weight bits, BF16 precision, tokenizer, rendered input IDs, greedy settings, EOS, and output and context budgets. Keep the original and optimized controls. The 3B optional draft requires the matching local adapter. The 35B DFlash2 draft is public. Only the original BF16 target may commit speculative output or persistent target state.
3. **Measure the complete cycle.** Split prefill, drafting, ranking, target verification, acceptance, state commitment, transfers, waits and streaming. Separate preparation. In 35B, measure CPU expert reads and PCIe gathers concurrently and count host bytes per committed token. Tune real verifier graph shapes using committed tokens per complete cycle. Verify attention ancestry, positions, EOS, and the accepted attention, recurrent and convolution state. Include discarded proposals and fallback work in timing.
4. **Implement, then verify.** Test one change at a time. Check full token IDs and stop reasons against each control. For strict changes, require exact token matches and check cache or other persistent state as appropriate. For separately labeled changes to floating-point evaluation order, identify the changed operation and measure both token matches and answer and format correctness, including paired regressions. Leave the original runner available.
5. **Benchmark and report.** Freeze changes before held-out evaluation. Alternate repeated warm runs with profiling off in streaming and non-streaming modes. Report preparation, time to first token, total request latency, token throughput, correctness, and results per workload. Keep browser and transport latency distinct. Compare against both frozen controls where available. Keep passing changes that improve held-out performance and provide exact reproduction commands. State what ran on real hardware and what remains unvalidated.
