# Lightreason hardware optimization

Work from the cloned Lightreason repository. Read `README.md` for setup, `docs/porting.md` for the backend workflow, and `docs/benchmarks.md` for the reference implementations and commands.

1. **Inventory and establish a baseline.** Record the device, memory, driver, OS, inference stack, and commit. Keep stock hardware settings. On the supported RTX 4090 setup, start with the target-only Qwen Standard CLI. For another NVIDIA GPU, verify BF16 support and run that same original CLI before changing anything. On ROCm, MPS, or CPU, establish a BF16 reference with the intended backend and audit CUDA-specific assumptions. Treat missing BF16 support as a blocker for the same-precision experiment. Require actual device evidence before marking hardware supported.
2. **Freeze the contract.** Preserve the target weight hash, BF16 precision, tokenizer, chat template, input token IDs, greedy settings, EOS IDs, and output and context budgets. Keep the original and any existing optimized runner as controls. The auxiliary draft and matching trained adapter are optional assets. Without an authorized copy of the adapter, work on the target-only path or use a separately labeled draft configuration. Only the original BF16 target may authorize speculative output and persistent target KV updates.
3. **Measure one complete cycle.** Use development cases to split prefill, draft, tree selection, verification, acceptance, cache commitment, CPU/GPU waits, streaming, and preparation. Account for overlapping waits separately from GPU kernel time. Optimize the measured bottleneck first. Use preallocation and suffix writes for coordination cost. For tree width, prepare true smaller verifier shapes, preserve supported depth and causal ancestry, and choose committed tokens per complete cycle time. Include any auxiliary work and fallback in timing.
4. **Implement, then verify.** Test one change at a time. Check full token IDs and stop reasons against each control. For strict changes, require exact token matches and check cache or other persistent state as appropriate. For separately labeled changes to floating-point evaluation order, identify the changed operation and measure both token matches and answer and format correctness, including paired regressions. Leave the original runner available.
5. **Benchmark and report.** Freeze changes before held-out evaluation. Alternate repeated warm runs with profiling off in streaming and non-streaming modes. Report preparation, time to first token, total request latency, token throughput, correctness, and results per workload. Keep browser and transport latency distinct. Compare against both frozen controls where available. Keep passing changes that improve held-out performance and provide exact reproduction commands. State what ran on real hardware and what remains unvalidated.
